# 用户与身份模型设计

- 状态：Draft
- 日期：2026-10-11
- 所属项目：full-stack-nextjs
- 相关架构决策：ADR-001 Modular Monolith

## 1. 设计目标

本设计用于定义个人消费互联网产品中的用户、登录身份和会话模型，为后续领域建模、认证集成、数据持久化、权限控制和安全测试提供统一依据。

### 1.1 设计目标

1. 建立稳定的产品用户身份，不依赖邮箱地址或第三方平台的用户标识作为产品主标识。
2. 支持本地账号与多个第三方身份提供商。
3. 将产品用户、登录身份、认证会话和授权决策明确分离。
4. 明确用户生命周期、身份关联、账号停用和会话失效的业务规则。
5. 采用成熟的认证解决方案，将自行实现的重点放在领域边界、集成方式、安全审查和业务规则上。
6. 通过自动化测试验证领域不变量、应用用例、持久化约束和安全边界。
7. 保持模块化单体架构，避免在尚无实际需求时提前拆分微服务。

### 1.2 目标能力范围

用户体系按照完整能力集进行规划，涵盖以下领域：

1. 用户生命周期与个人资料管理。
2. 本地账号、凭据管理及第三方身份提供商。
3. 邮箱验证、密码恢复、多因素认证和身份关联。
4. 会话生命周期、设备管理与会话撤销。
5. 用户角色、权限、资源归属与服务端授权。
6. 安全事件、审计日志、风险控制与速率限制。
7. 通知、数据导出、账号注销和数据删除。
8. 数据一致性、配置管理、可观测性、故障恢复和自动化测试。

所有能力都应具有明确的模块边界、配置契约、安全要求和验收标准。

### 1.3 分阶段实现原则

能力规划完整，不代表一次性实现全部功能。

每个能力按以下顺序推进：

1. 明确领域规则与安全边界。
2. 定义配置项、默认值和非法配置处理。
3. 设计应用用例和依赖端口。
4. 选择或实现基础设施适配器。
5. 编写单元、集成和必要的端到端测试。
6. 完成安全审查、运行验证和文档记录。

在能力尚未实现时，不得将其标记为已支持；在能力未启用时，不得将其暴露为可用功能。

### 1.4 配置与安全原则

- 功能是否启用由经过校验的配置决定，不通过随意散落的布尔判断控制。
- 每个开关必须定义默认值、适用环境、依赖条件、关闭后的行为和测试要求。
- 缺少必要配置时，系统应明确失败或安全地禁用相应能力，不得静默降级为不安全行为。
- 配置开关不得绕过身份验证、授权、数据隔离和领域不变量。
- 密钥、密码和令牌等敏感值不得提交到版本控制，也不得写入普通日志。
- 对安全敏感的配置变更和账号状态变更，应定义审计与验证策略。

## 2. 核心领域概念

### 2.1 User：产品用户

`User` 表示产品内部认可的一个用户主体，是用户资料、产品业务数据和后续授权关系所关联的稳定身份。

设计原则：

- 使用由本产品生成的稳定、不可变的用户 ID。
- 邮箱、昵称和第三方账号标识均不得充当用户主标识。
- 用户资料与认证凭据分离。
- 用户状态由明确的领域规则管理，不能由任意接口直接修改。
- 用户停用、注销和删除属于不同的业务操作。
- 对关键状态变更记录审计信息，但不得记录密码、访问令牌或其他认证秘密。

### 2.2 Login Identity：登录身份

登录身份表示用户通过某种身份来源证明自己身份的方式。

第一阶段支持：

- 本地账号，例如邮箱和密码。
- 第三方身份提供商，例如 Google 或 Apple。

第三方身份至少需要能够以提供商标识和提供商侧的稳定用户标识进行唯一识别。具体字段和存储方式由认证方案评估及数据库设计阶段确定。

设计原则：

- 一个产品用户可以关联多个登录身份。
- 一个第三方登录身份在本产品中只能归属于一个产品用户。
- 第三方提供商的用户 ID 不能替代本产品的 User ID。
- 邮箱可能变化、可能尚未验证，也可能在不同提供商之间重复，因此不能仅凭邮箱相同就自动合并账号。
- 身份关联与解绑必须经过明确的授权流程，并考虑账号接管风险。
- 不允许在未验证用户控制权的情况下，把已有登录身份转移给另一个用户。

### 2.3 Session：登录会话

会话表示一次已建立的登录状态及其有效期。

设计原则：

- 会话具有明确的创建、有效、过期和撤销语义。
- 会话有效不代表用户必然有权访问某项业务资源。
- 每次受保护的数据访问，都必须在适当的服务端边界校验会话及用户状态。
- 用户被封禁、停用或进入注销流程时，必须按既定策略限制或撤销会话。
- Cookie、令牌、过期时间和会话持久化机制属于认证集成与基础设施设计，而不是产品用户领域实体的职责。

## 3. 核心关系

第一版逻辑关系如下：

- 一个 `User` 可以关联零个或多个登录身份。
- 一个登录身份最多关联一个 `User`。
- 一个 `User` 可以拥有多个会话。
- 一个会话只代表一个产品用户的已认证上下文。
- 用户资料、登录身份和会话不应因为实现方便而被合并成一个无法区分职责的大型实体。

关系约束：

1. 产品用户 ID 一旦创建就不因邮箱变更、第三方解绑或昵称修改而改变。
2. 第三方身份的唯一性由提供商标识与提供商侧稳定用户 ID 共同确定。
3. 身份关联操作必须验证操作者对待关联身份的控制权。
4. 会话认证成功后，仍需检查产品用户的当前状态。
5. 授权必须结合请求操作、资源归属及业务策略独立判断。

## 4. 分层职责原则

### Domain

负责表达产品用户的业务规则、生命周期、不变量、领域事件和领域错误。

不依赖 Next.js、数据库驱动、Cookie API 或具体认证 SDK。

### Application

负责组织用户用例，例如创建用户、更新资料、停用账号、关联身份和注销账号。

通过端口定义与持久化、认证提供商及其他外部能力的交互，并控制用例执行顺序。

### Infrastructure

负责数据库访问、唯一性约束、认证库适配、事务、会话存储和外部服务集成。

负责把外部系统的数据映射为应用层可使用的类型，但不能绕过领域规则。

### Presentation

负责 HTTP 路由、输入解析、请求校验、响应 DTO 和错误映射。

不直接操作数据库，也不应在路由处理函数中散落完整的业务规则。

### Next.js 服务端数据访问边界

受保护的数据读取和写入应通过明确的服务端访问边界完成。会话验证、用户状态检查、资源归属验证和必要的授权判断应在可信的服务端位置执行。

不能仅依靠隐藏按钮、客户端路由跳转或前端状态保护业务数据。

## 5. 尚待决定的问题

以下问题在后续章节中逐一讨论，当前不提前作出未经验证的实现承诺：

- 用户创建后是否必须完成邮箱验证才能使用核心功能？
- 用户的 `pending_verification`、`active`、`suspended`、`deactivated` 和 `deletion_pending` 状态如何转换？
- 邮箱变更、第三方身份关联和解绑需要哪些验证步骤？
- 一个用户是否允许关联多个第三方提供商？
- 用户主动注销后，数据何时删除，哪些记录需要保留？
- 认证库负责哪些能力，产品领域和应用层保留哪些规则？
- 如何处理并发关联、唯一性冲突、会话撤销和审计？

这些问题必须在编码前得到足够明确的答案，并在后续通过测试验证。
